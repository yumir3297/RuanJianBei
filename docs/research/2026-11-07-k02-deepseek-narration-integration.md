# K02：DeepSeek 辅助理解与讲解链路融合方案

> 来源：本地知识工作树 `codex/knowledge-workspace` 的 2026-11-07 设计和调研记录。本文保留用户的方案表达及研究依据；“最终方案”指当时的设计方向，不表示已全部实施。当前能力与验收见 [知识整合记录](../integration/KNOWLEDGE_UNDERSTANDING.md) 和 [验收总表](../testing/TESTING_AND_ACCEPTANCE.md)。

日期：2026-11-07。状态：代码核查后的设计建议，尚未实施或调用付费 API。
前置资料：[场景考证与技术调研](2026-11-07-k02-source-research.md)。

后续统筹入口：[AI 全链路知识管理最终方案](2026-11-07-ai-knowledge-management-final-design.md)。本文保留代码核查与专项融合分析。

## 一、结论

把 DeepSeek 用作后台“资料理解与讲解知识编排器”：在导入后理解内容、拆分知识、关联景点、提取讲解主题和可回答问题。经过审核后，这些结果进入现有发布与检索流程，由现有游客端 LLM 按受众、角色和上下文生成讲解，再走 TTS 与数字人。

形成“离线知识理解 + 在线证据讲解”的协同流程。后台理解不置于每次游客请求的前面，避免增加在线等待；资料更新后通过现有知识代次使问答和讲解缓存失效。

## 二、代码现状与可复用部分

以下是静态代码核查结论，不代表本次运行验证。

| 环节 | 当前实现 | 融合含义 |
| --- | --- | --- |
| 文档解析 | `backend/app/services/knowledge/parsers.py`：JSON、文本 PDF；无文字页跳过，整份无文本时 needs_ocr | 需要多格式适配和混合页完整性检查 |
| 导入任务 | `knowledge/imports.py`：解析后生成修订草稿，保留页码与文件来源 | 在解析与草稿之间插入可恢复的理解任务，不能仅传更多文本 |
| 发布 | `knowledge/publication.py`：固定修订，切块、嵌入、向量准备、发布指针切换 | 加工字段须随修订固定，并传播到切块和索引 |
| LLM | `llm/openai_compatible.py`：基于证据的流式 Chat Completions，有超时、限并发和降级 | 可复用配置和 HTTP 连接管理模式；当前不是通用 JSON 抽取服务 |
| 证据提示 | `llm/prompt_builder.py`：参考资料、证据编号、角色、child/adult/expert、记忆上下文 | 把已审核知识内容与新增证据字段送入同一生成器 |
| 检索范围 | `qa/guided_selector.py` 使用 `RetrievalScope(source_entry_id=景点条目ID)` | 多份关联资料作为独立条目后，当前范围可能排除它们，必须改造 |
| 检索结果 | `rag/base.py` 的 RetrievedDocument 只有标题、正文、source、entry/revision ID 等 | 尚不能端到端携带来源块、关联景点及有效期 |
| 问答链路 | `qa/pipeline.py`：景点/主题解析、缓存、FAQ/RAG、证据来源、流式 LLM 与 TTS | 保留快路径；扩展证据装配而不是增加第二条问答主链 |
| 自动讲解 | `api/guide.py`：复用 QA pipeline，累积全文后整段 TTS | 目前只传景点名称，未传分众化 audience；引用标记被清理，未返回结构化来源 |
| 缓存 | 问答具受众键与知识代次；自动讲解键包含代次、景点、音色、模型 | 新增受众、编排版本、有效期逻辑时同步设计缓存 |
| 知识盲区 | `qa/blind_spot_tracker.py` 记录缺资料；`blind_spot_resolution.py` 当前通过 FAQ 解决 | 可增加“关联新知识并复核”的补料闭环，不能宣称已自动完成 |

特别注意：`metadata_json` 能存字段，不意味着检索器、提示词与页面已经使用字段。只有打通读写链路才算融合完成。

## 三、DeepSeek API 应承担的任务

### 1. 输入：可定位的内容块

先由解析器输出内容块，每块具有服务端生成的 `block_id`、类型、正文和来源定位。定位可以是 PDF 页码、图片区域、工作表行范围、网页段落或 ASR 时间段。解析器没有提供可靠坐标/时间戳时只保留可证实的粒度，不让 DS 编造。

每个理解请求携带有限的相邻内容块、已有景点 ID/名称/别名候选、分类白名单、必要的文档上下文。按章节和表格边界分批，不把整本书或整张超长表一次塞入上下文。

### 2. 输出：带证据引用的候选知识

DS 辅助完成：

- 区分历史介绍、运营公告、表格、串场语和无关文本。
- 生成适合检索的标题、分类、关键词与别名候选。
- 依据给定景点目录推荐关联，未知对象进入待确认；只能返回存在的候选 ID 或空值。
- 抽取事实与支撑原文，整理讲解主题及可回答问题。
- 识别表格条件和公告生效/失效时间候选；没有明确日期则留空并提示。
- 对同一主体的资料提出重复或冲突提示，不自动裁决真伪与覆盖人工编辑。
- 对疑似 OCR 错字提出原文/建议对照；专名、数字、年代改动须确认。

候选结构示意，字段名为设计建议：

```json
{
  "schema_version": "knowledge-card-v1",
  "cards": [{
    "title": "示例景点的建筑特色",
    "attraction_id": 12,
    "category": "历史文化",
    "content_type": "cultural_fact",
    "content": "依据材料整理的正文",
    "facts": [{
      "text": "材料中明确记载的事实",
      "evidence": [{"block_id": "b003", "quote": "对应原文"}]
    }],
    "topic_tags": ["建筑"],
    "answerable_questions": ["这个景点有什么建筑特色？"],
    "valid_from": null,
    "valid_until": null,
    "warnings": []
  }]
}
```

例中的 ID 仅用于说明，生产请求由服务端提供候选集合。来源 URL、页码、定位等通过 block_id 回查原始块，不能信任模型自行给出的定位。

### 3. API 与校验方式

新增 `KnowledgeUnderstandingService`，复用已有 DeepSeek 凭据配置，采用独立提示词、超时、并发和预算；不要通过问答 `stream_generate()` 假扮知识抽取，也不要让其“官方资料降级文本”被解析为 JSON。

DeepSeek 官方 [JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode)本轮已阅读：通过 `response_format={"type":"json_object"}` 和提示词 JSON 示例请求结构化输出；需处理空白 content 和截断。JSON 可解析不等于符合业务 Schema，更不等于事实正确。具体模型、兼容网关和参数支持以项目当前配置的小样本验证为准，不盲用文档示例模型名。

程序用 Pydantic 检查字段、长度、分类、景点 ID、日期顺序与来源块是否存在；核查引用片段能否在对应块中匹配。匹配只证明引用存在，事实是否被引用支撑仍需管理员审核。材料中的命令或提示语作为资料处理，不改变系统抽取规则。

空白、格式错误或截断最多进行有限重试/缩小分批；失败保留原始提取内容，允许人工编辑和仅重跑理解阶段。不自动发布，不使用模型自报置信度充当质量指标。

按原件 hash、解析版本、块集合、模型标识、提示词版本和景点目录版本生成理解缓存键。记录耗时、tokens、失败阶段及选用模型；后台并发池与游客讲解分开，若共用供应商额度还需给游客请求预留容量。

## 四、与讲解链路的六处融合

### A. 景点关联贯穿检索

引入明确的景点主体关联，区别于知识条目 ID：一个景点可以关联多个文稿、图片、公告和事实条目。当前景点本身使用“景点信息”知识条目作为入口，可先建立关联表兼容现有 ID，后续再演进主体模型。

`RetrievalScope` 增加景点主体范围，检索命中“景点主条目 + 与其关联的已发布知识”。切块、向量过滤、BM25、数据库回退都要执行相同语义与发布可见性；无关联的旧数据保持可检索。不要只扩大向量路径而遗漏其他回退路径。

### B. 知识卡片成为证据，而非新的无来源讲稿

正文进入现有切块/嵌入流程，来源块、原件版本、主体关联、内容类型、有效期随不可变修订保留。`RetrievedDocument` 和来源事件增加必要的定位信息，前端可从证据卡打开原文位置。

关键词和“可回答问题”作为辅助检索字段或查询提示，不能替换事实正文，也不自动写入高优先级 FAQ。模型总结可能遗漏的原文仍保留，避免只索引摘要造成效果倒退。

### C. 分众化复用同一事实底稿

后台产出事实、术语解释及主题标签，在线复用现有 child/adult/expert 与角色提示词：儿童口径减少术语，深度口径增加有依据的细节。首期不预生成三套相互独立的事实正文，降低多版本不一致。

事实、别名与解释建议区分存储；模型生成的比喻和表达建议不能成为历史事实证据。跨会话记忆只决定讲哪些主题与表达密度，不作为景区事实来源。

### D. 自动讲解使用可控的内容编排

当前 `/narration` 的“请介绍{name}”复用问答，仍受问答提示词的短回答约束。新增讲解用途和长度预算，使背景、特色、观赏要点有可控结构；编排只组织检索到的事实，不填补缺失事实。

讲解请求补充稳定景点 ID、受众等必要参数。讲解结果返回结构化来源；TTS 文本去掉引用标记，但界面仍显示证据。保留现有静态简介/浏览器朗读降级路径。

首期继续使用现有整段讲解音频；在线问答已有流式文字/TTS，不能把自动讲解也描述为已逐句流式播放。若增加讲解用途提示词，版本必须进入缓存键。

### E. 运营事实与时效管理

时间表保留项目、条件、时段及有效区间，管理员确认后发布。文化讲解优先文化事实；询问时间、票价时优先相关运营事实。

时效检查应在检索、FAQ 快路径、答案缓存和自动讲解缓存共同生效。自然过期不触发发布代次增长，因此还需有效边界限制缓存寿命或命中时重验；未知有效期不应假装永久最新，应提示人工维护。首期可暂不宣传时效自动过滤，先完成日期标注和审核，再打通全路径。

### F. 知识盲区驱动补料

后台展示游客未解问题及关联景点 → 管理员上传相关资料 → DS 提示可能覆盖哪些问题及证据 → 审核发布 → 用原问题回放检查检索和来源 → 管理员确认解决。

不因“导入成功”自动标记盲区已解决；现有 FAQ 解决功能继续保留。这个闭环可作为后续高价值亮点，完成后再称为知识运营反馈闭环。

## 五、渐进实施顺序

| 阶段 | 交付内容 | 最小验收 |
| --- | --- | --- |
| 1：理解底座 | 内容块、来源定位、DS JSON 抽取、候选卡片、原文对照与失败回退 | 少量文稿/图片/表格，事实可对照，空白/错误响应不阻断人工草稿 |
| 2：贯穿讲解 | 主体关联、发布索引传播、各检索路径兼容、证据定位 | 同一景点的多个独立条目能被指定景点问答检索；草稿不可见 |
| 3：演示融合 | 自动讲解用途、受众、结构化来源与缓存键 | 发布后问答及自动讲解更新，儿童/成人缓存不串用，TTS 降级可用 |
| 4：运营增强 | 时间表有效期、盲区补料、短录音/网页 | 过期缓存不泄漏旧运营结论，补料问题回放可核验 |

复用现有事务发布，不另建绕过审核的自动入库接口。后台任务应持久化理解阶段与产物，具备租约/心跳或等效控制；耗时解析不能依赖 `wait_for(to_thread())` 取消底层计算。解析引擎宜独立进程/服务并设置资源和超时边界。

## 六、比赛表达与展示脚本

推荐技术表达：**“DeepSeek 辅助的多模态知识理解与证据驱动讲解协同机制”。**

创新落点是：将格式解析后的内容进一步转成关联景点、主题与来源的知识卡片，并由同一事实底稿支持分众化讲解、问答和语音呈现。无需额外宣称自研基础模型或知识图谱推理。

展示脚本：

1. 上传同一景点的讲解稿、展牌照片和时间表，显示不同解析路径。
2. 展示 DS 识别的主题、景点候选、问题建议及来源片段，人工修正一处再发布。
3. 指定景点提问，命中新导入的独立知识条目并打开来源。
4. 对同一事实切换儿童与深度口径，展示事实一致、表达不同。
5. 自动讲解复用这些知识，语音播放，页面保留证据；发布更新后重新生成。

本轮仅完成调研记录和方案设计，不更改业务代码，不请求真实 DeepSeek API，不新增依赖。后续验证重点是少量真实资料和核心演示回归，不进行无必要的大规模性能评测。
