## 目标与范围

将原“扫描件 OCR”拓展为“面向文旅讲解的多源多模态知识加工模块”。比赛优先展示技术在真实场景中的组合应用，形成稳定的导入、审核、发布、讲解闭环；不以训练模型或大规模论文评测为目标。

### 场景中的关键问题

1. 表格不能简单摊平成连续文本：不同项目和日期的时间容易串位。
2. 历史文化与运营信息生命周期不同：临时闭园、演出排期需要有效期。
3. 文稿、展牌和台账可能描述同一景点：应关联到同一主体，保留独立证据与版本。
4. 正文提取不等于事实核验：网页可能有过时内容，OCR 可能读错专名、数字。
5. 官方网页也可能抓取失败：本轮灵山官网搜索结果可获取，但直接抓取发生传输错误，应提供粘贴正文入口。

## 二、候选技术与适配边界

| 环节 | 候选技术 | 建议与边界 |
| --- | --- | --- |
| 文稿转换 | MarkItDown 或格式专用解析器 | 原生读取为主；精确来源位置需专门保留 |
| 表格解析 | openpyxl、CSV 解析 | 先取行列，再由管理员确认字段对应；不要让模型重新猜整张表 |
| 扫描与版面 | MinerU | 优先验证候选，输出 Markdown/JSON；不同版本、本地与 API 的格式范围不同 |
| OCR 替代 | PaddleOCR PP-StructureV3 / PaddleOCR-VL | 支持版面、表格等文档任务；首期和 MinerU 路线择一，避免多引擎并行维护 |
| 网页 | Trafilatura | 单页正文与元数据抽取；复杂动态页不保证成功，保留 HTML/正文兜底 |
| 音频 | 现有 ASR 服务 | 复用供应商适配基础；长音频、时间戳、分段需额外验证 |
| 语义加工 | 现有 DeepSeek 接口配置，新增后台结构化任务 | 负责理解、分类、关联和抽取，输出必须校验并审核 |

MarkItDown 的图片支持不等于默认完整 OCR；官方说明中图像描述和语音转写依赖外部服务。MinerU/Paddle 的公开性能与语言覆盖不能直接写成本项目实测指标。Python、系统架构、模型内存及部署依赖须在确定版本后验证，重型解析独立运行。

## 三、推荐产品与技术主线

多源输入 → 自适应解析 → 统一内容块及来源定位 → 清洗、景点关联与知识卡片抽取 → 人工审核 → 发布 → 既有 RAG 和 AI 讲解。

知识卡片建议保留：标题、景点、别名、正文、内容类型、原始内容引用、来源位置、生效/失效时间、处理警告、审核状态。具体模型见[融合方案](2026-11-07-k02-deepseek-narration-integration.md)。

三个应用创新表达：

1. **自适应解析**：对原生文稿、表格、扫描页面、图片和录音采用不同处理路径。
2. **围绕景点的知识卡片化**：将不同来源转成统一字段和可追溯证据，参与讲解与问答。
3. **来源与时效协同管理**：保留版本及证据，提示重复、冲突和有效期；真正实现检索过滤后才能称时效感知检索。

## 四、比赛收敛范围与演示

优先完成文稿、表格、PDF/图片、知识卡片、审核发布；短录音及单页网页按时间扩展。古籍碑刻通识、长视频全面理解、全站自动采集作为扩展，不作为演示必经步骤。

主演示：同一景点的文稿、展牌照片和时间表 → 显示解析方式 → 关联知识卡片 → 修改并发布 → 游客问答使用新资料并显示来源。短资料现场真实导入，长资料可以展示明确标注为已处理的缓存结果。

稳定性底线：解析与游客请求隔离、限并发、保留原件、单文件失败隔离、失败可重试、模型失败回退提取原文、不得把空结果或遗漏扫描页当成功。验收用少量代表样本检查事实、数字、表格对应关系、发布可见性及游客链路回归。

## 五、文书素材

推荐名称：**面向文旅讲解的多源多模态知识加工模块**。

以下是实现目标表述，实现后才可改为成果陈述：

> 针对景区知识分散于讲解文稿、业务台账、展牌图片、扫描文献及讲解录音等载体，系统构建多源多模态知识加工模块，协同原生文档解析、OCR 版面识别、语音转写与大模型结构化抽取，将异构资料转化为关联景点实体的标准化知识卡片。通过保留原始资料、内容定位与处理记录，并结合人工审核发布机制，实现从原始资料采集到 AI 讲解知识供给的统一管理，提升景区存量资料的复用能力和知识更新便利性。
