# 景区安全守护与客流控制：远期设计来源

这份整理来自 Trae 来源工作区 `feat/location-guide-opt` 的 `docs/讨论优化/safety-guard-mode-2026-11-02.md`（2026-11-02，待评审草案）。它是远期设想和讨论材料，**不是当前实现、已确认需求或现场安全保障**。当前 CASS 首版及验收边界见 [CASS 功能](../implementation/CASS_GUIDE.md) 和 [验收总表](../testing/TESTING_AND_ACCEPTANCE.md)。原稿仍在来源工作区，本整理不代表其全部 API、参数或数据表已采用。

## 目标与原则

原稿希望为大型景区提供可选的辅助安全模式和匿名客流建议，明确不默认监控所有游客，不承诺室内精准定位、医疗判断、摔倒检测或绝对安全。游客应获得单独说明并能拒绝、关闭和撤回；拒绝不妨碍普通导览。管理端启用景区功能不等于游客同意。原稿提出入口二维码/NFC 与围栏校验、园内上报、离园停止和短期删除，但可行性、授权、留存时长和责任主体均待确认。

客流与安全应分成不同目的和权限：普通运营只看符合隐私要求的区域聚合，安全值班人员仅在获授权的场景查看必要个人位置，并记录访问与处置；位置不进入普通日志或广告画像。原稿提出按设备去重、标注来源、时间与置信度，并对小样本隐藏具体值；**上报设备数不等于实际人数**，设备覆盖不全或一人多设备均会影响估计。阈值、网格大小和留存时间是待验证建议，不应直接作为已确定政策。

## 交互、控制与约束

草案考虑游客主动 SOS、危险区、路线偏离及长时间停留等提示，并由值班人员处置。AI 可辅助组织提示或摘要，风险规则、权限与处置由确定性机制和人工负责；分流建议属于软控制，限流、封路、闸机或广播等硬控制须人工确认。现行版本没有后台接警、人员调度或自动救援，不得据此显示“已受理”或承诺到场救援。

纯 Web 在关闭页面、锁屏和后台时不能保证持续定位，室内或遮挡环境精度也有限；位置可能被模拟。后续若要推进，需先确认数据来源及使用授权、定位质量、告警误报、设备和网络条件、访问审计、留存及删除机制，再用目标场景实测。真实危险区、路线、联系人和救援接收方均须由景区核验。

## 待决事项与验收方向

草案留下的决策包括：入口和同意方式；数据源与校准方式；具体区域、角色、查看权限和位置保留时长；同行人共享；以及是否接入票务、闸机或救援系统。这些尚未因本次整理而得到批准。

未来验收需分别检查同意/拒绝/撤回、园内外边界和权限拒绝、位置过期删除、访问审计、设备去重及低样本保护、模拟数据标识、误告警和人工处置。安全与客流链路的目标、数据范围、权限和保留周期需分别验证；模拟浏览器和本地测试不能替代现场与真实接警验收。
