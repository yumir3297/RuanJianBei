# 前端设计与双端边界

## 当前结构

| 应用 | 入口 | 主要职责 | 禁止混入 |
|---|---|---|---|
| 游客端 | `frontend/apps/tourist/` | 数字人、问答、地图、行程、设备交互、离线陪游 | 管理 token、管理 API、后台图表和管理导航 |
| 管理端 | `frontend/apps/admin/` | 登录、知识、资源、审核、发布、分析和数字人预览 | 游客对话、游客匿名行程和游客播放状态 |

两端可使用不同 origin、静态目录和构建产物，共用后端 API；前端拆分不能改变后端权限、cookie、CSRF 或游客 owner 契约。

## 设计原则

- 游客端保持一个连续舞台，地图、路线、问答和讲解工具共享游客运行时状态。
- 管理端使用独立 router、认证 store 和管理依赖；游客包不加载管理 token 或管理组件。
- 共享逻辑放在身份中立的 transport、schema 或状态协议中；单端交互放在对应 app 或视图中。
- 安全、定位、播放和行程分别有明确的权威来源；组件通过相应 store、composable 或服务端版本读取，不另造相互冲突的状态。
- 聊天、定位、播放及部分情境请求通过请求代次、目录摘要或 revision 校验隔离迟到结果；其他异步流程仍需逐项验收。
- 设计文档中的“支持”必须区分源码核对、浏览器冒烟、真机实测和生产验收。

## 已确认的视觉与交互方向

面向缺少定制预算的景区，通用产品以中性视觉为基础；名称、Logo、背景、导游形象、文案、主题及功能由景区配置，示例景区不应固化为通用页面。户外自然光、触控、清晰中文、对比度与键盘焦点是设计目标，不能代替实际设备测试。

早期产品设计要求采用清晰的中文字体与可配置主题，主要操作和正文优先考虑 14–16px、普通文字对比度目标 4.5:1、交互热区通常至少 44px；窄屏优先换行、收起或重排，不靠缩小重要文字适配。实际可访问性须按页面、设备和缩放状态验证。模块标题、启停、顺序和内容可配置，通用主题、景区数据与模块代码分别维护；空数据、长名称、加载失败和缺少素材均需有明确状态。尊重减少动态效果设置，数字人动作与面板反馈不应互相抢夺注意力。

游客端以中央数字人和语音操作为焦点，导览工具与讲解设置位于两侧；记录和资料按需展开，移动端使用底部入口与弹层。背景可由运营替换，风景与人物应保持连续，功能面板承载复杂背景上的阅读内容。设计经历过无遮罩与统一深色面板两个版本；最终视觉应以现有界面及实际验收为准，不把早期固定宽度当成全设备承诺。

管理端采用用户选定的**中性浅色工作台方案 A**，优先服务内容维护：以清晰的导航、知识编辑、盲区处理、数字人预览和运营分析组织页面。Logo、景区名称和主题色体现景区特征；避免装饰渐变、发光效果、英文眉题和无意义指标卡。统计只展示有真实数据来源的值；加载失败要提示并保留已有内容，不能以零值掩盖失败。编辑失败应保留输入，未保存离开需提示；未实现的预览或音色试听不能伪装可用。

桌面、平板和手机应分别检查导航折叠、输入和弹层、键盘焦点、缩放与文字换行；设计稿曾以 1024、736 和 390 像素进行原型检查，这不构成实际设备兼容性结论。管理端视觉稿和游客端样式演进保存在 Git 历史中，当前界面能力以源码和[验收总表](../testing/TESTING_AND_ACCEPTANCE.md)为准。

### 地图自动讲解的设计意图

游客主动开启自动讲解后，可根据可用定位提供附近景点讲解；普通自动讲解应避让正在进行的对话和播放，等待期间应重新检查触发条件，避免离开后播放过期内容。用户可停止或重听；定位不可用、精度不足、模拟巡游及服务降级须明确提示。定位权限、坐标系、音频自动播放限制和实机行为需要分别验证；历史方案的阈值与按钮位置不作为当前承诺，现行路径及状态见 [代码地图](../REPO_MAP.md) 和 [共享状态盘点](../integration/GUIDE_STATE_INVENTORY.md)。

Trae 的定位方案还提出“接近预取 → 停留确认 → 播放 → 离开 → 再进入可重听”，用滞回和冷却减少密集景点重复触发；降级到模拟位置时不应自动冒充真实到访，游客主动选择模拟巡游才按演示流程触发。隐藏地图时停止定位与待播请求，播放操作应遵守会话所有权。浏览器 `heading` 表示移动方向而非视线方向，不宜作为“看向景点”的硬门控；专门看景模式可另行研究。这些是来源设计与待核验方向，参数不是现场测得的通用阈值。参考 [MDN heading](https://developer.mozilla.org/en-US/docs/Web/API/GeolocationCoordinates/heading) 和 [Android 地理围栏](https://developer.android.com/develop/sensors-and-location/location/geofencing)。

### 照片识景的确认方向

模型候选是识别线索；游客可从已发布景点目录明确选择，也应能表示不确定或没有匹配。目录不可用、同名歧义及照片与已有景点选择冲突时应清楚提示，不能静默认定；用户选择也不能证明照片识别正确。换图、清除或重新分析后，旧确认和迟到结果不能套用到新图片；提交前还需验证目录版本和发布状态。以上包含历史交互设计及待验收场景，实际覆盖以源码和[验收总表](../testing/TESTING_AND_ACCEPTANCE.md)为准。

### 移动地图的已确认方向

用户要求地图占据操作页面，减少卡片遮挡：地图铺满可用空间，景点、路线、图层和园区信息使用一个可收起的互斥面板；拖动地图不带动页面，列表在面板内滚动。景点可就地显示名称及讲解入口，聊天时保留地图。定位失败须如实提示，模拟位置和演示客流须明确标注，示意路线不宣称真实导航。这是设计及历史浏览器仿真记录，实际设备结论见验收总表。

### 离线陪游的已确认方向

用户原话是“游戏画面之外上下的内容全部删掉，画面主体就是游戏页面，其他功能模块散布在画面不同合适位置”。来源方案据此采用全屏游戏画布与四角浮层：地图、求助和跳跃入口放在易触及的位置，网络恢复只提示并由游客决定是否返回；纸雕、水墨与低饱和自然色用于保持景区氛围。布局应避免遮挡角色和障碍，同时考虑横竖屏、安全区、键盘、读屏和减少动态效果。

**当前差距：**主线离线页源码仍采用独立页头、地图和求助区以及带边框的游戏区，并非上述全屏浮层方案。这个方向作为后续视觉验收目标保留，不代表现已实现；离线缓存、地图及求助资料的实际边界见[离线陪游记录](../integration/OFFLINE_COMPANION.md)。

## 前端验收边界

- 构建和静态边界检查通过，只证明依赖闭包和产物隔离；不证明真机能力。
- 管理端登录、知识发布、资源操作需使用管理员 token；游客 origin 不得读取或转发该 token。
- 摄像头、麦克风、GPS、系统音频、微信 WebView、键盘和后台恢复必须按设备矩阵逐项实测。
- 离线缓存只属于游客端；不缓存管理员凭据、聊天响应或游客私有行程。
