## 1. 推进原则

1. 先完成能够独立使用的完整链路，再增加下一组功能。
2. 先修复现有数据与交互链路，再扩展上传、社区等能力。
3. 优先复用现有模块；是否引入新服务或依赖，在对应功能讨论时决定。
4. 弱网、多端和防御性设计贯穿各阶段；并发先建立基线，再按瓶颈优化。
5. 每项先讨论用户流程、输入输出、失败处理和验收方式，确认后再细化实现。
6. 第一轮按“知识更新一致性 → 异常与弱网 → 语速与重播 → 拍照识景”讨论和实施。
7. 浏览器网页端性能和适配作为跨阶段要求：每个功能结合涉及的终端、能力和弱网场景验收；先测量现状，再确定优化目标。

## 2. 现有链路与需要补齐的环节

### 2.1 游客问答链路

```text
文字输入 / 语音识别结果 / 图片识别线索
    → 问题与上下文整理
    → FAQ / 知识检索 / 路线推荐
    → LLM 回答或已有内容降级
    → 流式文字 + TTS 音频
    → 字幕、口型、表情与播放状态
    → 游客反馈
```

已有入口包括聊天、拍照识景、地图讲解和预设路线。后续应统一请求状态、取消、失败提示和播放控制，让不同入口具有一致的体验。

### 2.2 知识更新链路

```text
人工编辑 / 预处理资料同步 / 后续文件上传
    → 知识条目
    → 切块
    → 向量索引更新
    → 相关缓存失效
    → 检索验证
```

代码基线中，知识 CRUD、预处理资料同步和向量重建属于不同流程。知识 CRUD 直接更新条目；切块更新发生在资料同步中；向量构建读取已有切块。新增、修改或删除知识后，需要建立明确的一致性流程，避免条目已经变化而检索仍使用旧切块或缓存。

### 2.3 代码现状的几个约束

- 当前自动讲解存在进程内缓存和锁，扩容时需要重新评估共享与失效策略。
- 普通音频与流式 PCM 使用不同播放路径；语速、字幕与口型要分别验证。
- 游客端聊天提交的语速目前固定为 100；管理端语速偏好存于当前浏览器，尚未形成统一的游客播放设置。

- 定位含真实定位和模拟巡游模式，涉及安全和求助时必须识别位置来源。
- 现有路线和地图讲解有部分降级能力，仍需完善断流、长时间无数据、离线缓存和恢复流程。

## 4. 第一轮：按顺序讨论的四个工作包

### 4.1 工作包 A：知识更新一致性

**目标**：后台知识变化能够正确反映到切块、向量检索和缓存。

**拟定链路**

```text
编辑 / 新增 / 删除
    → 保存知识变化
    → 更新对应切块
    → 更新索引
    → 失效相关缓存
    → 发布状态与可检索状态一致
```

**讨论范围**

- 自动同步还是显式“发布”；发布期间游客读取哪一版内容。
- 单条更新、删除、批量导入的切块与索引处理。
- 索引失败后的状态、重试与旧版本可用性。
- 全量重建期间的查询行为，避免删除集合后出现服务空窗。
- 知识、切块、索引与答案缓存的版本或失效规则。

**验收场景**

- [ ] 新增知识后，能通过相应问题检索到新内容及来源。
- [ ] 修改知识后，回答与引用使用更新内容。
- [ ] 删除知识后，切块、索引和缓存不会继续暴露已删除内容。
- [ ] 更新失败时，后台显示失败环节并支持恢复；游客端有明确可用状态。
- [ ] 索引重建期间的查询行为经过验证。

### 4.2 工作包 B：异常、防御性设计与弱网基础

**目标**：断网、超时、上游故障和异常上传时，用户能看懂当前状态并继续操作。

**拟定链路**

```text
发起请求
    → 连接 / 接收 / 完成
    → 成功：保存结果与状态
    → 失败：保留有效内容 → 明确提示 → 可恢复或重试
```

**讨论范围**

- 普通请求、流式问答、图片、ASR、TTS 的超时与取消。
- 流式连接建立后的无数据超时、提前结束与部分回答标记。
- 区分用户停止、网络中断、服务不可用和请求不合法。
- 哪些操作可以有限自动重试；写入操作如何防重复。
- 上传前压缩与提示；服务端大小、实际格式、像素或时长边界。
- 正式部署凭据、登录与高成本接口限流。
- 静态简介、预设路线、文字保留等已有降级体验。
- 分段耗时、失败率、资源消耗和基础并发测量。

**验收场景**

- [ ] 连接超时、流中断、流长期无数据都能结束等待。
- [ ] 已收到的文字保留，未完成回答有明确标记。
- [ ] 用户停止后，旧请求不会继续覆盖新请求的状态。
- [ ] 重试不会产生不受控的重复提交。
- [ ] 不合法或超限文件有明确反馈。
- [ ] 上游语音服务失败时文字仍可用。
- [ ] 记录首次文字、首次音频、完整回答耗时和失败率基线。

### 4.3 工作包 C：讲解语速、重播与播放状态

**目标**：聊天和地图讲解具有统一、可理解的播放体验。

**拟定链路**

```text
游客选择语速
    → 保存个人偏好
    → 播放器或 TTS 按确定策略应用语速
    → 字幕 / 口型 / 进度同步
    → 完成后可重播，播放中可停止
```

**讨论范围**

- 游客语速控件位置、范围和保存方式。
- TTS 生成时调速与播放时调速如何选择，避免叠加。
- 普通音频、流式 PCM 和浏览器朗读分别如何支持。
- 重播优先复用音频；音频不可用时是否重新合成。
- 当前回答、历史回答与地图讲解的播放互斥。
- 播放停止、页面切换、自动讲解触发时的状态恢复。
- 音频缓存键包含哪些因素，以及容量与有效期。

- [聊天状态与流事件](../../frontend/src/stores/chat.js)

- [地图讲解](../../frontend/src/views/tourist/MapView.vue)
- [自动讲解接口](../../backend/app/api/guide.py)

**验收场景**

- [ ] 游客修改语速后，约定支持的播放路径正确应用设置。
- [ ] 字幕、播放进度和口型随实际音频时间变化。
- [ ] 当前回答与地图讲解都能重播、停止。
- [ ] 多次点击或切换入口不会导致音频叠加。
- [ ] 重播是否重新调用 AI 或 TTS 有明确且可观察的规则。

### 4.4 工作包 D：拍照识景完整链路

**目标**：游客能从图片得到可确认的景点识别结果，再获得有依据的讲解。

**拟定链路**

```text
拍照 / 选择图片
    → 方向与尺寸处理、压缩
    → 上传校验
    → 提取场景 / 文字 / 候选景点
    → 歧义确认或补充描述
    → 检索官方知识
    → 生成带来源的讲解
```

**讨论范围**

- 自动处理图片的尺寸、质量和识别效果之间的取舍。
- 候选为空、候选冲突和低把握结果如何交互。
- 图片线索与官方事实来源的区分。
- 是否合并当前两个操作步骤，保留哪些用户确认。
- 识别结果的缓存、失败恢复和来源追踪。
- 评测样本包含地标、指示牌、文字牌、非景区照片和模糊图片。

- [拍照能力](../../frontend/src/composables/useCamera.js)
- [识景界面](../../frontend/src/views/tourist/ChatView.vue)

**验收场景**

- [ ] 支持约定格式；超限、损坏文件和失败请求可恢复。
- [ ] 歧义识别不会直接当作确定景点输出。
- [ ] 最终讲解引用知识来源，识别线索不被当作官方事实。
- [ ] 每阶段耗时可记录，并可用固定图片集重复评估。
- [ ] 手机拍照、相册选择和弱网中断均经过验证。

## 5. 第三阶段：内容生产与游客分享

### 5.1 文件上传与 OCR

在工作包 A 完成后讨论。复用现有知识条目、切块、索引和来源结构。

```text
管理员上传
    → 识别文件类型
    → 提取文本 / 扫描件 OCR
    → 保留文件、页码、段落来源
    → 预览与修正
    → 发布到知识更新链路
    → 检索验证
```

先支持明确的一组格式，再逐步扩展；不同格式采用对应解析器。长任务需要进度、失败原因、取消或重试机制。先定位现有 OCR 工具代码，再决定复用或适配方案。

- [ ] 确认首批格式、大小及页数边界。
- [ ] 确认 OCR 工具位置与运行方式。
- [ ] 确认预览、纠错与发布流程。
- [ ] 同一文档重复上传有明确处理规则。
- [ ] 发布后的引用可追溯到原文位置。

### 5.2 总结图片导出

“游览／讲解总结生成分享图片”为当前暂定理解，具体范围待讨论。

```text
选择要总结的讲解 / 景点 / 路线
    → 组织摘要
    → 游客预览与编辑
    → 分享卡排版
    → 保存图片
```

先采用受控图片、字体和卡片组件，单独验证长文本、跨域素材、失败占位及手机保存体验。

### 5.3 美图

“游客照片的基础美化”为当前暂定理解，具体范围待讨论。

```text
选择 / 拍摄照片
    → 裁剪、旋转、亮度或滤镜
    → 景区相框 / 文案
    → 预览
    → 保存或主动选择上传
```

基础编辑可以先在浏览器内完成。照片编辑与总结卡可复用素材、导出能力，但应保留各自清楚的操作入口。

### 5.4 离线内容延伸

在弱网基础上讨论应用外壳、基础资料和主动下载的讲解缓存。缓存展示版本、更新时间和清理入口。云端实时生成与已下载内容需要有可辨识的状态。地图离线资源另行确认数据来源、授权和技术方案。

## 6. 第四阶段：定位、求助与真实客流

### 6.1 真实定位与自动讲解

```text
请求定位授权
    → 真实位置、精度、时间与来源
    → 坐标处理与景点匹配
    → 进入 / 离开范围判断
    → 触发或排队讲解
```

- [ ] 验证设备坐标、字段、坐标系转换和地图显示。
- [ ] 区分真实、模拟、精度不足、过期、拒绝授权和不可用状态。
- [ ] 验证进入、离开、返回同一景点和播放忙时的行为。
- [ ] 手机权限与定位失败状态可理解、可恢复。

### 6.2 求助入口

```text
游客主动打开求助
    → 展示核实后的景区联系方式
    → 获取可用的真实位置 / 手动描述
    → 展示位置时间与精度
    → 拨打电话、复制或分享位置
```

求助链路不使用模拟坐标。若扩展为后台接警，另行确认接收人员、送达与受理确认、超时处理和演练方案；发送与受理应分别显示状态。

### 6.3 人流与路线

```text
真实客流数据源
    → 标准化区域、人数 / 热度、时间与来源
    → 数据有效性检查
    → 地图展示
    → 参与路线评分
    → 向游客解释推荐依据
```

现有演示估算应明确标记。先确定景区数据源，再确定接入与推荐逻辑。数据过期或不可用时退回预设路线，并展示相应状态。

## 7. 第五阶段：情绪、社区与容量优化

### 7.1 情绪分析

从前面阶段积累可用于评估的反馈；具体采集范围、保存方式和有效期单独确认。

```text
文本 / 可用语音信号
    → 情绪或服务需求判断
    → 冲突与低把握处理
    → 选择响应策略
    → 游客反馈或纠正
    → 离线评估与改进
```

先评估现有规则对否定句、反问、噪声和紧急表述的效果，再决定是否引入新模型。代码设定的分数与经数据校准的概率应区分；紧急需求保留独立处理规则。

### 7.2 社区小贴士

先完成景点下的小贴士闭环，后续再讨论更完整的社区。

```text
发布文字 / 图片
    → 校验与审核
    → 展示
    → 评论或反馈
    → 举报、隐藏与管理
```

依赖上传、存储、身份与权限设计。官方资料与游客内容保留明确来源；社区内容进入导览知识库需要另外的审核和发布流程。

### 7.3 针对性并发优化

按固定工作负载比较首字、首音频、完整响应耗时、成功率、CPU、内存和上游调用消耗。根据结果依次讨论缓存、连接复用、限流、排队、批处理与任务隔离。容量目标和服务器配置待讨论，不预设当前可承载人数。

## 8. 跨阶段要求：浏览器网页端性能、多端与弱网

### 8.1 交付目标与实施顺序

浏览器网页端是主要交付形式：游客通过手机扫码访问，兼顾电脑和平板。优先验证微信内置浏览器、iOS Safari 和 Android 常用浏览器；具体机型、浏览器版本及性能目标在基线阶段确定。当前基于 Vue 3 + Vite 按需优化，具体组件拆分和依赖调整按测量结果讨论。

前端性能基线放入第一阶段，与工作包 B 的链路耗时测量协调进行；后续功能按各自影响范围持续优化和回归，不改变第一轮四个工作包的讨论顺序。各项均为计划，具体方案、数值目标和实现状态待讨论。

### 8.2 前端开发优化要求

- **首屏与按需加载**：记录首次打开、页面可交互、数字人可用和地图可用的时间；分析构建产物及首屏下载资源。评估地图、路线等非首屏功能按需加载，比较实际构建及真机测量结果。
- **数字人与低性能设备**：分析模型大小、帧率、内存和设备发热、耗电表现；评估画质档位、减少特效、页面不可见时暂停或降低渲染，以及 WebGL 不可用时的简化形象。暂停与恢复不得破坏音频、字幕及口型同步。
- **资源与弱网**：评估图片和数字人模型压缩、静态资源缓存、下载时机和失效策略；在慢网、中断及恢复场景显示加载、失败与重试状态。离线内容范围按第 5.4 节另行确认。
- **浏览器能力适配**：对录音、摄像头、定位、音频自动播放与 WebGL 进行能力检测；权限被拒绝或能力不可用时提供清楚提示和可用的替代操作。
- **前端架构**：评估聊天页面、播放器、数字人和地图的职责边界与按需加载；拆分应服务于可维护性和实际性能，拆文件本身不作为性能提升的证据。
- **性能测量**：记录设备、浏览器版本、网络条件和构建版本，在相同条件下比较改动前后结果。首屏指标关注首次可见、可交互、数字人与地图可用；运行阶段关注帧率、内存、卡顿与请求失败率；热量和续航可通过可复现的真机观察补充评估。问答还分别记录首字、首音频和完整响应耗时，区分前端与服务器、外部 AI 等待。
