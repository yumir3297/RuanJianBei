# 双端 AI 工作台：功能链路与分阶段路线图

首次整理：2026-10-27。重构日期：2026-10-28。代码核对基线：`672a104`。

用户已明确同时建设游客端和景区运营端，并要求新增待开发清单、重构规划。本轮将原功能补完路线图重组为双端任务闭环；以下阶段排序为整理后的建议，业务尚未实施。

任务、状态、细项验收与原始需求追溯统一维护在[双端 AI 工作台待开发清单](2026-10-28-ai-workbench-backlog.md)。本文只维护产品方向、阶段、依赖与交付门槛；现有实现见[功能地图](../REPO_MAP.md)。

## 1. 产品目标

游客端帮助用户规划、修改、执行和记录一次游览；运营端帮助景区导入资料、生产讲解、审核发布并处理游客反馈。两端以已发布景区内容连接，形成可验证的服务改进闭环。

浏览器网页为主要交付形式。游客以手机扫码、语音和现场操作为主；运营端强调内容编辑、对比、预览与发布，兼顾电脑和平板。业务对象共享，布局按任务与设备设计。

工作台的交付标准：用户任务能够保存、继续、修改和完成；成果能够编辑、追溯与交付；失败可定位并恢复。聊天、数字人、地图、识景和图表分别服务这些任务。

## 2. 对原方案的调整

保留原有数据一致性、异常处理、性能基线与多端要求。将原来按功能逐项补完的顺序改为先建立两个完整闭环，再接入扩展功能：

1. 运营知识闭环：上传 → 草稿修正 → 发布 → 游客检索新版。
2. 游客行程闭环：描述需求 → 行程草稿 → 编辑/对话修改 → 开始 → 中断后继续。
3. 内容与反馈闭环：讲解生产 → 预览发布 → 游客反馈 → 运营待办 → 修订复测。

原 14 项需求全部保留，映射见待开发清单第 9 节。美图、完整社区和复杂情绪优化后移；识景、播放、定位和导出围绕当前任务接入。第一轮不再固定采用旧版 A→B→C→D 的功能顺序，以本次阶段依赖为准。

知识工作区已有[确认设计](../superpowers/specs/2026-10-27-knowledge-workspace-design.md)，状态为“设计已确认／待实施”，不再重复标为待讨论。其他新增工作台模块仍需具体设计。

## 3. 架构演进边界

以下为目标职责，不能视为当前实现：

| 层次 | 目标职责 | 优先复用 |
|---|---|---|
| 双端交互 | 游客当前任务、运营编辑与待办；设备适配 | Vue 页面、Pinia、composables、数字人舞台 |
| 任务与成果 | 游览上下文、行程修订、成果引用、任务状态与恢复 | 现有会话、访客、知识与反馈实体，新增独立业务对象 |
| 工具与流程 | 可观察的检索、识景、推荐、讲解、导入和发布执行 | QA、视觉、ASR/TTS、推荐与数据导入服务 |
| 内容与证据 | 来源、不可变修订、发布可见性、缓存代次 | SQLAlchemy、repository、Chroma 与 FAQ |

游客行程与运营草稿分别鉴权；后台不能因能看统计而默认读取全部私人照片或位置。共享内容以景点 ID、知识来源与发布版本关联。

继续使用 Vue 3、FastAPI 与现有服务边界；允许在现有技术栈内重构职责，不以更换语言、框架、微服务或多智能体为前提。已有[多景区草案](../superpowers/specs/2026-10-02-multi-scenic-guide-proposal.md)作为配置和隔离设计参考，未实施部分不作既成能力。

首版可先在单景区完成闭环；若采用共享多景区部署，必须先完成服务端身份、成员关系以及数据库、检索、缓存、任务、成果与统计的景区隔离。

## 4. 分阶段交付

| 阶段 | 工作包 | 主要依赖 | 交付门槛 |
|---|---|---|---|
| 1 基础与运营知识闭环 | K01、F01、C01 基线 | 现有服务；已确认知识设计 | 修正后发布，游客引用新版；失败保留旧版；下架及缓存失效；异常可恢复 |
| 2 游客任务与行程闭环 | W01、V01、W02、R01 首批 | 稳定景点 ID、内容读取、异常基础 | 同一行程可手动和对话修改、保存、开始并恢复；任务有状态与权限 |
| 3 识景、讲解与成果生产 | V02、V03、K02、O01、W03 | 两个首轮闭环、任务与版本基础 | 识景关联行程；讲解可预览发布；总结先编辑保存再导出 |
| 4 双端反馈与现场增强 | O02、V04、V05 | 已发布内容、反馈、真机定位；客流需数据源 | 问题到修订发布复测可追溯；真实位置与数据状态可辨识 |
| 5 扩展体验与容量 | E01、E02、E03、E04 | 游览记录、审核、样本与测量基线 | 扩展服务已有任务；社区可审核；情绪与容量有测量依据 |
| 贯穿各阶段 | C01、F01 回归、R01 按需演进 | 各功能涉及设备及链路 | 手机、桌面、弱网、权限、停止与旧响应隔离经过适用范围验证 |

这是依赖顺序，不表示同阶段必须一次性全部上线。K01 的持久发布任务先按原设计实现；W02 后续复用其经验，不等待通用任务框架而阻塞首个闭环。R01 随业务边界逐步拆分，不进行脱离闭环的大规模搬文件。

## 5. 首轮验收场景

### 运营知识闭环

上传约定格式资料 → 保留来源进入草稿 → 修改后发布 → 游客提问引用新版。未发布草稿不可见；批量准备失败保留旧版；删除后向量、FAQ、数据库回退及缓存不再返回失效内容。发布中编辑、任务重启与重复提交均不破坏版本。

### 游客行程闭环

输入“老人和孩子、三小时、少走路” → 确认必要条件 → 生成可编辑草稿 → “去掉一个景点、增加休息时间”修改原行程 → 用户确认开始 → 记录完成/跳过 → 中断并恢复继续。

不得将预设路线换一段推荐理由当作可编辑行程；缺开放时间、步行路网或客流时应标记估算与未知。首轮不依赖持续 GPS、真实客流或完整社区。

### 双端连接

运营发布的内容版本能够被游客回答与讲解引用；后续反馈可关联问题和内容来源。私人行程不自动公开，运营草稿不进入游客检索。

## 6. 共用验收与证据

每个工作包按影响范围记录：

- 输入、结构化输出、持久化结果、权限归属和来源版本。
- 成功、空结果、失败、取消、重试、并发修改、旧响应及服务重启。
- 手机与电脑、横竖屏、软键盘、长文本、录音/相机/定位拒绝、音频中断和 WebGL 降级。
- 设备与浏览器版本、网络条件、代码版本；首屏、首字、首音频、完整回答及必要资源指标。

实际检查入口见[开发指南](../DEVELOPMENT.md)与[多端矩阵](../COMPATIBILITY.md)。不因构建或后端测试通过就宣称真机兼容、完整闭环或并发能力达标。

## 7. 开工前需补齐的依据

- 归档适用赛题原文及评分标准，建立需求—工作包—演示场景—验收证据映射。
- 对应工作包明确游客恢复身份、首批格式与 OCR 位置、行程数据约束、成果保存和删除、运营角色与预览发布规则。
- 真实客流、求助接收方、社区边界和容量目标随相关阶段确定，不阻塞无需这些条件的首轮闭环。
- 本路线图和清单是产品规划。新增模块需形成具体设计与实施计划，再修改业务代码；既有确认设计保持有效。
