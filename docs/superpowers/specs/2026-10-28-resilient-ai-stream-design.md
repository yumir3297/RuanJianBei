# 面向景区弱网的 AI 工作台传输与恢复设计

状态：实施中。日期：2026-10-28。

2026-10-28 执行调整：用户要求不间断研发。已有实现采用 SSE 15 秒心跳，默认连接 20 秒、无数据 45 秒、无进展 90 秒、总时限 180 秒；调用可覆盖，须结合实际模型和部署复测。模型分众改写 FAQ 时暂缓文本与语音，最终回退时统一展示和播放官方原文，代价是该分支首字/首音延后。PCM 弱网缓冲为受控实验，默认关闭，仅 `VITE_GUIDE_ADAPTIVE_AUDIO=1` 构建时启用；固定模拟轨迹不代表现场收益。生产代码仍需按文末门槛完成验证。

## 目标与范围

面向手机扫码游览与运营工作台，在 Vue 3/FastAPI 内改善问答、语音和后续任务的响应、停止、错误恢复及可观测性。先交付聊天纵向闭环及可重复测量，随后对接识景、讲解及 K01 持久任务；行程对象、完整任务平台及音频断点续传另行设计。每阶段保留移动端输入、数字人及现有接口行为，按实际设备验收。

创新候选是把任务/内容版本约束、不同媒介的恢复规则及播放缓冲反馈结合到景区场景；单个技术均已有先例。实验前不宣称原创协议、首创或具体提速。

## 方案选择

推荐渐进式方案：沿现有 SSE 和现有语音路径增加终态、超时、请求隔离与观测；之后为真实的长任务增加持久执行和版本关联；最后比较自适应语音策略。另一方案是先建设完整通用 Agent/工作流平台，统一迁移所有入口：扩展性更强，但依赖身份、任务模型和 K01 最终契约，当前收益及改造成本未经验证。用户已要求按前述创新方向进行正式设计与研发，因此本稿采用渐进方案；不以引入新协议、框架或模型为交付前提。

## 首批：聊天可靠性与体验

### 流与终态

沿用现有 `status`、`text_chunk`、`text`、`sources`、`audio`、`audio_chunk`、`avatar`、`error`、`done`，兼容旧消费者；成功必须收到 `done` 并结合服务端生成终态，已有 `text.is_complete` 只代表文字阶段完成。已有 LLM 中断路径也可能发送 `done` 及 `degraded`，所以需明确区分中途截断与完整降级回答，不能将所有 `done` 等同完整。`error` 或网络异常保留已有文字和引用，显示“回答未完成，可重试”；无文字时提供明确失败提示；手动停止单独标为“已停止”。不能把 EOF 当成功，也不将部分内容拼接错误文案充当结构化状态。重试创建新的交互轮次，已显示内容不静默覆盖。

前端每轮使用独立 generation token 与 AbortController。所有事件、异常、finally、异步解码及播放回调在更新共享 store/播放器前校验所属轮次。切换/停止立即使旧轮次失效并停止其音频；旧 promise 完成不得关闭新轮次状态、结束新 PCM 流或重置新播放器。新旧播放互斥沿用共享播放器，不创建第二个 Three.js/VRM 舞台。

### 超时与清理

连接、无网络数据、无业务进展和最长总时限分开，均可配置并在基线实验后定值；现有 20 秒连接上限作为初始兼容值，其他参数首批以可配置测试值及实际供应商延迟确定，避免凭空将慢模型误判失败。心跳可刷新网络存活时间，不能刷新业务进展时间；状态变化、文字、有效音频等可定义为进展，重复同一 status 不无限延长等待。计时采用单调时钟；区分用户主动停止、超时、离线、HTTP 错误和异常断流。服务端取消传播及 TTS/LLM 任务清理需验证，不能承诺远端供应商必然停止计费。

读取器、定时器及 abort listener 在成功、错误、取消和超时均释放。SSE 测试覆盖 UTF-8 与 CRLF 跨块、注释、分帧、坏 JSON、半帧断开。只有完整合法帧进入处理器；错误不会被误记为正常结束。

### 文本、语音、字幕

以消息状态分别表达文字结果和语音状态：文字可完成而语音失败；失败时不丢失文本，重试语音仅在已有可支持入口和可靠的片段定位条件下开放。流式 PCM、整段音频和浏览器朗读各自沿用现有能力，不承诺统一续播。播放相关回调区分音频接收、调度和实际开始；字幕及嘴型仅随当前有效轮次更新。用户停止后文字可留存、音频及嘴型立即停止。

不默认执行高成本重试；用户主动发起的新生成可能再次调用模型。等待、失败、停止及可恢复提示应在手机屏幕可见，保留现有输入、文字阅读与无 WebGL 回退。弱网不自动删减事实、约束或引用。

### 指标与隐私

前端以单调时钟记录发起、首文字到达、首次音频数据、音频在运行中的 AudioContext 上调度、结束与取消；文字到达不等于可见，音频调度不保证用户听见。后台记录阶段耗时、提供方类别、请求关联、终态与可统计错误类别。对无法观察的显示或听觉输出标记不可测，不用入队或资源下载冒充。前后端时钟不直接相减；按各端时长和关联 ID 分析。默认不收集提问、答案、照片、位置、token 或完整音频；记录聚合指标的范围、保存期限及关闭方式由具体部署决定。可借鉴 OpenTelemetry 语义，但 GenAI 约定仍在演进，需记录选用版本，不作为首批部署依赖。

## 后续：任务恢复与版本协同

只对业务需要跨连接运行的长任务引入独立任务 ID、所有者、阶段、结果引用、输入修订、内容来源版本、幂等键与恢复记录；聊天首批不伪装为持久任务。创建、提交状态和成果关系须具备事务边界；断线查原任务，不能盲目新建。重放/重试涉及副作用时对操作端保障幂等或先对账，外部系统不支持时必须表达结果未知。权限在服务端逐次核验，匿名本地 ID 不当授权凭据。

按实际业务使用版本检查：用户修订变更后结果只作为候选；来源知识变更时提示复核；内容下架必须服从 K01 实际可见性与发布约束。恢复任务状态、恢复成果、恢复事件是三种不同能力。事件补发仅在持久事件序列、鉴权、去重和保留策略具备时承诺；音频及嘴型不承诺逐块续传。长任务必须有可恢复的执行器或已验证的 K01 执行机制，不能仅以 SSE 心跳或任务表替代。

## 后续：自适应输出实验

先记录现有 TTS 分段规则、首次可听时间、卡顿、缓冲和调用费用；固定输入与供应商、设备、网络条件，比较现有固定规则与有界规则策略。候选输入：已确认播放缓冲、生成和接收速度、断流；候选动作：首段大小、缓冲门槛、限制预生成量及推迟可选资源。适配当前供应商支持的参数；不假设支持改变码率、取消单片段或对 PCM 已播放部分精确定位。必须评估中文韵律、重复/遗漏文本、字幕嘴型同步、调用次数和费用。结果不优则保留现有策略。

## 验证与交付门槛

1. 仓库映射校验与业务针对性测试；服务端事件、前端解析、store 和播放器联动验证。前端目前无 test 脚本，实施计划必须选用项目可执行的轻量测试方案，不能凭空写 `npm test`。
2. 对照稳定、限速高延迟、抖动、中断/恢复：比较首字可见、首个音频数据、实际开始播放、完成、卡顿、成功率、开销。测试次数和统计方法在运行前固定，保留 P50/P95、样本量、失败率与原始记录；模拟网络与现场网络分开。
3. 故障：连接建立前失败；连接成功后无数据；心跳但无有效进展；分帧中断；部分文字后无 done；旧请求晚失败；播放解码晚返回；TTS 失败但文字有效；用户停止与立刻新发；刷新和服务重启。不得将完成误报为成功或让旧响应影响新操作。
4. 桌面与手机真实浏览器：微信内置浏览器、iOS Safari、Android 常用浏览器记录机型、版本、网络、权限；未实测明确标记。音频自动播放限制、页面切后台与低性能 WebGL 必须实际核对。测试不能由桌面仿真代替真机。
5. 完成时同步 `REPO_MAP.md`、必要架构与兼容矩阵，记录实际代码版本、测试命令和未覆盖范围。K01 的发布/恢复实证另以其最终分支和验收结果为准。
