# V01 可验证的连续伴游规划设计

日期：2026-10-29。状态：已由用户批准；实施中。

## 1. 已确认方向与意图

用户选择“可验证的局部改线”：保留人工调整和已游记录，突出可控、可恢复。继续使用 Vue 3、Pinia、FastAPI、Pydantic、SQLAlchemy 与 Alembic。

实现“描述需求 → 可编辑草稿 → 手动或对话修改 → 比较差异 → 确认保存 → 开始游览 → 完成/跳过 → 中断后恢复”。游客通过表单和自然语言操作同一份行程；模型不直接获得数据库写权限。

调研证据及既有能力边界见 [V01 调研](../../research/2026-10-29-v01-itinerary-research.md)。除用户选择的方向外，下文细节均为本轮建议，不视为用户已逐项确认。

## 2. 方案取舍

| 方案 | 取舍 | 结论 |
|---|---|---|
| 模板与手动编辑 | 交付较快，连续对话修改价值较弱 | 作为首个实现里程碑和降级路径 |
| 模型解释意图 + 程序校验 + 局部修改确认 | 保留现有成果，收益可测，适配已有持久修订 | 用户已选择 |
| 完整 Agent 自动重规划 | 适合复杂跨城研究，但依赖更多数据、任务调度和成本控制 | 不纳入首轮 |

## 3. 首轮边界

- 单景区、同浏览器匿名身份；复用 W01 Cookie、CSRF、所有权、修订和幂等。
- 支持空白创建、模板生成、指定同行人/分钟预算/兴趣/必去与排除/步行偏好/休息需求。
- 手动增删、上下移动、修改停留或休息时长、锁定条目；移动端不依赖拖拽。
- AI 支持补充约束、添加、删除、替换、移动景点与调整休息/停留时长；语义不明时追问。
- 草稿确认后开始；手动记录当前、完成、跳过；恢复同一已保存任务。
- 缺开放时间或路网时可保存“未验证草稿”，开始前说明未知范围；不得宣称可达性已保证。已知硬冲突必须先解决。
- 不纳入跨设备账号、实时 GPS、真实客流、自动订票、精确导航、导出、多景区权限或通用 Agent 平台。

## 4. 接入与并行开发约定

W01 已在另一个对话验收，禁止直接修改 `/private/tmp/ruanjianbei-w01`。实施从已验收提交 `a8c2837` 的独立检出开始；当前主工作树 F01/V03 改动保持原样，只有确认依赖后才审阅导入。不能以 `672a104` 为唯一基线假装已经包含身份与修订。

W01 基线没有发布 revision；V01 集成 K01 提交 `914c030` 的只读可见性契约。适配器 join `KnowledgeEntry.published_revision_id` 对应的 `KnowledgeRevision`，过滤 `withdrawn_at`，且只使用该 revision metadata 中导入的 `attraction_id`。K01 当前未为每条 entry 保存 `site_id`，因此此适配器仅绑定现有单景区 `Settings.site_id`，请求其他 site 时拒绝；多景区隔离需 K01 增加每条知识的 site id 后再扩展。

新增行程 API 与服务，不更改普通问答文本 SSE 契约。ChatView 仅装配上下文与工具；新的行程编辑与提案面板拆成组件。前端行程 store 与聊天消息 store 分离。

## 5. 稳定身份与版本化快照

- `schema_version=2`；读入 W01 老快照时补齐默认字段，生成并持久化条目身份的新修订，旧修订原文不变。
- 景点身份使用 `(site_id, spot_code)`，优先复用 metadata 的 LS 编码；知识数据库整数 ID 只用作当前内容引用。发布修订 ID 独立保存。
- 目录拒绝同景区重复代码、歧义别名和未知代码，不按数组位置或地图名称猜测身份。无代码的地点可作为未解析人工备注，不能伪装为已验证景点。
- 每次停留/休息有独立 `stop_id` UUID，区别于景点 ID；允许明确重访时用不同 stop_id。同地点重复出现不能被自动去重。
- 条目 `kind=visit|rest`；景点条目含 spot_code、原始显示名、内容版本引用；休息条目没有虚构景点/设施 ID。
- 条目含 duration_minutes、duration_basis=`source|user|estimate|unknown`、依据引用、locked_fields、created_by=`manual|ai|template`。来源的可信级别由服务端赋值，模型不能自报 verified。
- 约束含同行人、available_minutes、兴趣、required/excluded 的景点码、walking_preference、休息策略。未知字段保持 null。老人/孩子不自动等于无障碍需求；不得无依据宣称无障碍。
- `legs` 记录相邻停留的旅行时间与依据，未知为 null；不以演示经纬度推断精确步行。界面显示已知小计/估算区间及未计入的未知段，不能把 null 当 0。
- 时间按分钟预算与相对顺序表达；没有日期与经核验时窗时不生成“今天保证开放”等承诺。文字 `opening_info` 作为资料提示，不能直接当机器可执行时窗。

## 6. 手动与 AI 共用修改协议

服务端提供纯函数式操作引擎。输入为基线快照、allowlist 操作和目录，输出候选快照、结构化 diff 与校验报告。

操作按类型显式定义，不接受任意 JSON Pointer：`add_visit`、`remove_stop`、`replace_visit`、`move_stop`、`set_duration`、`add_rest`、`update_constraints`。用 stop_id 和 before/after_stop_id 定位，不允许模型写 owner、版本号、内容真实性、进度或锁定字段。最多 20 个操作、50 个条目；Pydantic 拒绝额外字段。开始后的剩余预算调整属于独立进度事件，模型只能提出目标分钟数，截止时间由服务端按第 8 节计算。

锁定项默认不被 AI 改动。游客可手动解锁后再编辑；AI 不能自行解锁。必去与排除冲突、修改锁定项或已完成条目时返回原因与可选择的解决方法，禁止静默放宽需求。

人工编辑立即更新本地草稿并显示未保存；服务端保存同样经过校验，不能绕开规则。AI 在包含当前本地草稿及其摘要的基线上生成提案，必须保留本地未保存修改。

## 7. 模型与约束检查分工

1. 前端明确“修改当前行程”的上下文；普通景点问答继续走 QA。主输入框只有在修改意图明确且绑定当前任务时才转行程操作，含混时让游客选择问答或改线。
2. 服务端验证身份、任务归属和基线版本，取得限定候选目录。
3. 专用 `ItineraryIntentService` 调用现有配置对应的模型，将文本转为操作或追问。不得复用会把错误转成普通讲解文案的 `stream_generate` 结果去执行。
4. JSON schema 校验操作；候选 ID、约束及权限再次由程序校验。模型无法提供权威路程、开放状态或进度。
5. 单次解析失败允许最多一次有界格式纠正，总预算内失败则保留草稿、返回可理解错误及手动入口。不递归重试或自动换成整份重写。
6. 校验后展示 diff、预算变化、保留项、冲突与未知信息。游客确认后才提交，确认过程中不再次调用模型。

模型传入的是必要约束、当前草稿、候选目录和本轮请求，不默认发送完整聊天历史、照片或位置。模板/规则降级必须标注，不假称 AI 已成功理解。

## 8. 约束、预算与最小修改

硬规则：身份与目录合法、排除项不加入、必去不丢失、锁定不变、已游事实不变、分钟为正、已知时长不超预算、顺序引用有效。新增约束与当前状态冲突时先提问。

软偏好：文化/摄影/亲子、少走路、休息频率。仅在有相关依据时排序；无路网时“少走路”表达为较少停留点/沿模板顺序的近似策略，并显示局限，不能保证实际距离更短。

预算为停留 + 休息 + 有依据的路段时间 + 明示预留量；未知段不当作 0。输出 `pass|conflict|unverified`，区分已知可行与数据不足。

预算口径：草稿中的 `available_minutes` 是从开始游览算起的整趟预算。确认开始时服务端记录 `started_at` 与 `finish_by = started_at + available_minutes`。开始后校验当前及未来的待执行部分，对比 `finish_by - 服务端当前时间`；已完成/已跳过历史保留，但不再占用未来预算。当前停留剩余时间优先用游客明确输入；否则使用完整计划停留时长作为保守估算，不能把按钮记录当作实际移动测量。当前位置到下一点无可靠路段信息时继续标记未验证。

“现在还剩 60 分钟”转为显式 `set_remaining_budget` 意图：以本轮请求的服务端接收时间为锚点提出新的 finish_by，差异中展示旧/新结束时间及其影响。它必须与改线一起确认；确认时重新按当前时间检查，不把等待确认的时间免费补回。暂停讲解或切后台不会自动延长预算；游客可以明确延长。不能一边按原始 180 分钟、一边按剩余 60 分钟重复放宽预算。旧任务没有开始时间则追问/由游客补充剩余预算，不回推虚假的实际耗时。开始后的时间预算调整写独立事件；撤销计划修订不回滚真实时间或预算截止事件。

局部修复优先满足明确修改，再保留未指定条目的身份、顺序、时长与锁定。首版在受限候选集内枚举允许的局部插入/删除/替换位置，用确定性排序比较硬冲突数、无关字段改动数、改动条目数和有依据的偏好得分；限制搜索量，超限追问或提供手动入口。不承诺全局最优。

模型可解释选择原因，服务端报告实际校验结果；解释不能代替约束检查。“改少一点”不能覆盖用户明确提出的必要大修改。

## 9. 提案、确认与故障恢复

建议新增 `ItineraryProposal` 表：owner_id、tour_id、base_version、draft_digest、catalog_digest、操作、规范化候选、diff、validation、状态、有效期和请求幂等指纹。提案私有，不进入 RAG。仅保留必要结构化内容，不持久保存模型推理。

建议 API：

- `GET /api/itinerary/catalog`：当前已发布景点与可用的计划数据。
- `POST /api/tour-sessions/{id}/itinerary/proposals`：自然语言/模板/手动操作产生预览；写请求沿用 Cookie、CSRF 和持久幂等。
- `GET /api/tour-sessions/{id}/itinerary/proposals/{proposal_id}`：读取自己的提案或生成状态，刷新可恢复。
- `POST /api/tour-sessions/{id}/itinerary/proposals/{proposal_id}/apply`：校验 expected_version、draft_digest 与目录版本后原子创建修订、事件和确认回执。
- 进度操作接口在第 10 节定义；不是模型可调用工具。

客户端上传本地草稿仅为提案基线，服务端重新校验所有字段和来源；服务端不信任客户端的 content_version 或 resolved 标记。确认时保存服务器计算的候选，客户端不得夹带替换快照。

提案生成先写持久请求占位并在短事务后释放锁，再调用模型；并发同键返回已有状态，不持有数据库事务等待模型。生成总预算建议 25 秒，专用客户端超时 35 秒，不受普通 HTTP 10 秒默认值误伤；该数值为待实测初始配置。

请求执行期间若进程崩溃，过期占位标记失败，原行程不变；不承诺后台继续。网络中断可查询已完成提案；如外部调用已发生而结果丢失，只能说明重试可能再次产生供应商费用，不宣称外部调用恰好一次。

确认同键返回相同修订。同键异内容、其他标签页改动、本地草稿变动、提案过期或目录变化返回明确冲突，不自动覆盖或无提示重算。前端停止仅取消本次展示与请求，迟到提案不得自动应用。

提案默认 30 分钟过期；清理、归属过滤和游览永久删除联动清理必须实现。未应用提案可刷新恢复，但在成功应用前不标为“行程已保存”。

## 10. 游览执行与撤销

任务状态沿用 draft/active/completed。用户确认开始后，进度以独立 `TourProgress` 与追加事件保存，不与计划修订混为一体；按 stop_id 关联 pending/current/completed/skipped，最多一个 current。

服务端提供开始、标记当前、完成、跳过、结束的显式命令；携带 expected_progress_version 和幂等键。开始与应用改线按同一任务锁/原子版本条件串行化，防止刚完成的条目被并发改线删除。应用提案同时校验生成时的进度版本。

已完成/已跳过事实不被 AI 改线覆盖。当前点需要改动时单独提示；未来点可正常改线，已游条目保留为历史。首轮允许手动纠正误标，产生纠正事件；AI 不能执行。

撤销行程变更通过旧修订创建新修订，先与当前进度合并校验；撤销不会把已完成改回未完成。若旧版缺少已游条目，保留历史并要求处理冲突，不能直接走绕过规则的全快照恢复。W01 的直接保存/历史恢复接口也必须接入同一校验，避免旁路。

未保存的本地编辑刷新后可能丢失，明确提示；只承诺已保存修订和执行事件恢复。Cookie 不可用时保留临时模板/手动体验，保存与 AI 提案提示需要匿名身份。

## 11. 与地图、聊天和数字人融合

- 路线列表仍可选模板，但“采用”创建/修改当前草稿，不把模板描述拼成一个新的聊天答案当作行程。
- 地图读取当前确认行程 stop_id/spot_code，坐标有证据时才落点；未知地点只显示清单，不套用代理坐标。
- “介绍当前景点”把 spot_code 映射为服务端当前有效 entry_id，交现有 selection/QA；游客私有行程不会写入公开答案缓存。
- 规划修订记录引用版本，回答生成使用当前有效已发布知识；旧版本下架后只保留行程中的历史引用摘要，不能凭旧引用继续读取下架内容。来源变更提示复核。
- 数字人可朗读提案摘要和当前景点讲解，沿用 V03 播放互斥、停止和语速；未经确认不宣布“已为你改好”。
- 规划结果和事实讲解分开标识，不把模型修改解释当作官方知识证据。

## 12. 验收与创新证据

核心演示：输入老人孩子/三小时/少走路 → 展示分钟预算与未知段 → 手动锁定梵宫并加休息 → 对话删一个景点 → 显示差异且保留锁定 → 确认开始 → 完成一个点 → 再改线 → 刷新继续，已游记录保持。

必须覆盖：歧义名称、必去与排除冲突、预算无法满足、缺路网、无效模型 JSON、伪造景点/来源、模型超时、重复确认、并发本地编辑/跨标签页保存、进度与提案竞争、内容下架、历史恢复旁路、Cookie 拒绝、跨游客读取，以及手机按钮与长文本。

创新表达采用“约束保持、局部修复、事实保护、证据追溯、连续讲解”的系统组合。用调研文档中的三组对照与保持率、完成率、未知披露、恢复一致性、时延和用量形成证据。不宣称首次提出局部修改或多视图行程，也不在测量前写性能提升比例。

## 13. 留给实施者的常规选择

组件/模块拆分、索引名、SQLAlchemy 锁的跨数据库实现、目录摘要编码与测试 fixture 组织可由实施者决定，但必须通过并发与迁移测试。实现计划需明确 PostgreSQL 与隔离 SQLite 的差异；不能用仅内存锁证明多进程正确。

代码实现前需要审阅本设计；批准后再制定逐步实施计划。首个里程碑是稳定目录、快照升级、手动编辑和事实进度，第二个是受限 AI 提案与确认，第三个是地图/讲解联动和评测。
