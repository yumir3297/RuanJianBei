# W02 工具执行与任务恢复设计

日期：2026-10-29。状态：用户已选择“现有数据库 + 小型执行器”并授权开发；W02 内核代码已在隔离分支实现，生产业务接入与行为验证未完成。
依据：[调研与接入核查](../../research/2026-10-29-w02-durable-execution-research.md)、[待开发清单](../../plans/2026-10-28-ai-workbench-backlog.md)。

审阅记录：此前 builder check 结论为 `nothing important left`。开发分支以 W01 实际身份、修订和事务边界为准；代码实现不代表迁移已运行、并发行为已验证或业务闭环已完成。

## 1. 目标与范围

游客和运营能看到真实执行步骤，知道哪些结果已保存、失败在哪里、是否可以重试；重启或重连后可查询原任务，允许恢复的流程从适用的已完成步骤继续。自动执行只产生候选或草稿，行程确认和运营发布仍调用各自业务命令。

保留 Vue 3/Pinia、FastAPI、SQLAlchemy、Alembic。用户已选现有数据库 + 小型执行器；不新增 Redis/Celery/Temporal/图框架依赖。DBOS/Temporal 的收益与取舍见调研，未被选择。

首轮分两层：先适配已有业务任务与统一查询，再给明确需要后台执行的流程提供 SQL 持久执行能力。W01/K01/V01 基线未整合前可用隔离 fixture 验证内核，但不能宣称业务闭环已完成。

不承诺浏览器离线仍可操作、跨设备恢复、供应商调用恰好一次、任意工具执行、任意 DAG、多智能体或普通聊天逐 token 续播。V01 现有崩溃失败规则不因 W02 改变。

## 2. 三种身份与三种状态

- `tour_id`：一次业务游览，沿用 W01；`chat_session_id` 只关联聊天。
- `job_id`：一次明确输入和目标版本的工具执行；一次业务游览可有多个 job。
- `step_key` 与 `attempt`：步骤的逻辑身份与执行尝试分离，同步骤重试不创建第二份业务成果。

业务状态、执行状态和成果状态分别保存。生成完成表示候选已保存，不表示行程已确认或知识已发布。

建议 job 状态：`queued/running/retry_wait/waiting_user/succeeded/failed/cancelled/stale`。结果不确定表现为 `waiting_user` 加 `reason=external_outcome_unknown`，不能当成普通失败自动重试。所有状态转换由服务端限定，前端不能直接指定状态。

## 3. 领域所有权与适配器

K01 持续拥有发布作业和生效事务，V01 持续拥有提案及 apply，W01 持续拥有游览和修订。已有任务用投影适配器读取其状态；同一个外部任务不能同时由旧执行器与 W02 worker 执行。

每个工具注册固定 Pydantic 输入/输出、工具版本、授权检查、重试策略、超时、成果类型和恢复模式。只注册代码内允许的工具，不接受客户端传函数路径、SQL、任意 URL 或任意操作 schema。

恢复模式为 `query_only`（只查现有结果）、`manual_retry`（允许用户决定重试）、`durable_resume`（明确支持后台恢复）。V01 提案初期为前两者；K01 通过其原执行机制恢复；新增讲解草稿生成可在后续 O01 批次使用第三种。

API 层负责输入与归属，服务层负责状态机及适配，repository 负责原子条件更新。不要在任务内核重写推荐、QA、发布或行程约束算法。

## 4. 建议持久对象

| 对象 | 关键字段与约束 |
|---|---|
| `ToolJob` | id、主体类型及主体 ID、site_id、目标类型/ID、tool_name/version、workflow_schema_version、输入摘要及必要结构化输入、base_revision/progress_version/content_digest、状态、reason、截止时间、created/updated；外部任务映射有唯一约束 |
| `ToolStep` | job_id、step_key、状态、input_digest、result_ref、attempt、最大尝试、next_run_at、error_code；唯一 `(job_id, step_key)` |
| `ToolAttempt` | job/step、attempt、开始/结束、provider_request_id（如可用）、调用是否可能发出、脱敏错误、用量；不保存密钥或模型内部推理 |
| `ToolEvent` | job_id、单调 seq、类型、摘要、结果引用、时间；唯一 `(job_id, seq)`，与状态更改同事务提交 |
| `ToolCommandReceipt` | 主体、命令、逻辑键、请求摘要、回执；唯一 `(principal_type, principal_id, command, key)`，同键异内容冲突 |

worker 领取字段包括 `lease_owner/lease_until/fence`。幂等 scope 不用未认证的 session_id。后台身份使用现有服务端管理员主体；若当前仅单管理员，明确按单管理员部署，不虚构多角色成员系统。

回执建议保留 7 天，明确去重保证窗口；成果本身用领域唯一键长期防重复。作业和步骤结果建议保留 30 天，待确认业务成果沿用各自过期/保存规则。过期清理不能提前删去仍有效回执依赖；用户删除优先于 TTL。照片、录音和完整聊天不默认复制到作业表。

## 5. 领取、续租与恢复

1. 创建命令在短事务中写 job、必要 step、回执和事件，提交后返回；不持事务等待模型。
2. 独立 worker 进程轮询数据库，API 进程只受理与查询；进程管理与健康检查必须包含 worker。
3. PostgreSQL 用短事务锁定可执行行（可用 `FOR UPDATE SKIP LOCKED`），写租约并递增 fence；提交后再做外部调用。
4. SQLite 用独立适配路径，以短写事务/条件更新领取，处理 busy 并有界退避；演示部署限制一个 worker。跨进程 fencing 仍需条件校验，不能只靠 Python 锁。
5. 续租和步骤完成必须同时匹配 job、lease_owner、fence、未过期租约及允许状态；失去租约的旧 worker 不能写状态、事件或成果引用。
6. 租约过期仅代表可核查，不代表外部调用未发生。安全纯计算可以重排队；结果不确定的外部调用进入查询或待用户决定。
7. 启动扫描与周期扫描使用同一原子领取路径；不能把所有 running 无条件置为 queued。取消、已删除、过期、未知工具版本的任务不恢复。

初始建议：租约 30 秒、10 秒续租、排队轮询 1 秒；步骤时限由工具声明，超过租约的操作须独立续租；均是待测配置，不是性能承诺。数据库故障或续租失败时停止推进和提交，外部操作尝试取消，无法取消则按不确定结果处理。

## 6. 步骤结果、重试与提交

步骤划分为读取候选、生成候选、校验、保存候选；外部模型调用单独成步。已完成结果仅在输入摘要、工具版本、来源可见性及适用内容版本仍满足时复用。

| 情况 | 处理 |
|---|---|
| 读取超时、明确未发出调用、可安全重复的计算 | 工具允许时有界退避重试，默认最多 3 次（含首次），不跨总预算 |
| 输入错误、权限拒绝、硬约束冲突、未知工具版本 | 不自动重试，返回可解释原因 |
| 供应商可能完成但本地未存结果 | 有远端查询/幂等能力先核查；否则 waiting_user，说明再次尝试可能增加费用 |
| 本地成果提交成功但响应丢失 | 查询原命令回执，不能重新生成或另建成果 |
| 基线行程、进度或目录变化 | 标为 stale/待复核；保留原候选，不静默套用或自动重算 |

候选、步骤完成和对应事件尽量在同一数据库事务中提交。行程 apply、发布仍使用业务层已有原子命令与独立幂等键；W02 不通过“先写成果再补成功标记”的双写绕过业务事务。跨存储准备（如向量）采用可重复准备 + 最终业务可见性检查；不承诺跨库原子提交。

W01 现有 repository 方法自行 commit。集成时必须增加可组合的事务服务/提交回执查询，不能简单在外层加 transaction 后宣称所有写入原子。业务提交路径要同时核对有效 job/fence、权限与目标版本，或使用同事务可验证的提交授权；旧租约不得通过业务 API 旁路写入。

## 7. 取消、确认与事实保护

断开页面/SSE 只是停止观察；“取消任务”是显式服务端命令。取消在同一 job 锁下使 fence 失效、阻止后续候选提交，再合作式取消外部调用。取消不保证撤销供应商费用，也不撤销已提交的业务事实。

取消与完成并发时，以数据库事务先成功者决定结果：已经成功则返回成功及成果；取消先成功则旧 worker 不能保存候选。已提交行程需要用户通过 V01 修改/撤销，不用任务取消回滚。

人工确认必须绑定 proposal_id、版本、草稿摘要、进度版本和必要的目录摘要；用户确认时重新校验，必要时展示新的差异。开始/完成/跳过、手动锁定与知识下架都可能使旧候选不再适用。

W02 复用 V01 apply 和进度命令，不新增绕过入口。游客私人行程不写公共 RAG；运营草稿不因 job succeeded 而对游客可见。

## 8. 观察与界面接入

建议在现有游览/运营页面显示执行卡：真实步骤、已保存结果、失败原因和可用下一步。状态服务独立于 chat store，工具展开不重挂载数字人。

首版采用有界轮询和事件游标，后台隐藏时暂停轮询，返回页面先查快照；后续可增加 SSE 作为通知加速。数据库是事实来源，通知丢失不影响恢复。事件只含摘要与成果引用，不把音频二进制或模型推理写入事件。

建议游客接口：`GET /api/tour-sessions/{tour_id}/executions`、`GET .../executions/{job_id}`、`GET .../executions/{job_id}/events?after_seq=...`；命令通过具体已注册工具入口创建，另有显式 retry/cancel。运营接口使用独立鉴权路径。以上均为拟定接口，不是已存在路由。

所有读写重新检查主体、景区及目标归属，游客写操作沿用 W01 Cookie/CSRF；事件 ID 和 job_id 不能充当凭据。列表分页和轮询频率有上限。事件清理后返回游标过期信号和快照恢复方式，不假装连续日志完整。

## 9. 删除、过期与升级

业务任务进入回收站后停止新执行并使租约失效；恢复业务对象不自动恢复已取消计算。永久删除级联清理任务输入、候选引用、事件和回执中的私人数据，外部原始文件按原存储策略删除。worker 在完成提交事务中重新检查删除标记，防止删除后重建数据。

工具版本和 workflow_schema_version 固定在 job；部署后只能由兼容 handler 恢复。缺 handler 时失败并说明升级不兼容，不运行最新代码猜测旧步骤。清理器同样有条件更新、并发保护和可验证日志。

## 10. 分批开发与验收门槛

1. **基线与适配**：冻结 W01/V01/K01 实际接口，记录分支和迁移依赖；提供统一执行摘要及 query_only 恢复，不创建第二个发布执行器。
2. **持久内核**：实现作业/步骤/回执/事件、独立 worker、租约 fencing、有界重试；使用隔离数据库和假工具验证进程崩溃及竞争。
3. **首个业务接入**：优先接已确认需要后台恢复的内容生成流程；在 O01 未设计前只交付适配/内核验证，不提前宣称 O01 完成。V01 可先接查询、冲突和原提案确认。
4. **多端与证据**：手机恢复操作、弱网、切后台、事件游标和实际 PostgreSQL 多 worker；完成对照评测与卖点证据。

必须故障注入：入队提交后响应丢失、领取后进程被杀、外部调用前/后崩溃、候选提交后响应丢失、租约过期旧 worker 复活、两 worker 竞争、取消竞争、不同游客读取、手动编辑与进度更新、知识下架、删除与回收站、旧版本 handler、事件游标失效。

硬性要求：无重复业务成果、无静默覆盖、无跨游客读取、无下架内容复活、无租约失效写入。需同时证明有效任务能够完成，报告恢复成功率、调用/用量和 p50/p95。SQLite 自动化通过不能替代 PostgreSQL 多进程或真机验收。

## 11. 留给实施者的选择

模块拆分、SQL 索引名、批量领取大小、序列实现、事务 unit-of-work 组织和测试 fixture 由实施者决定，但必须满足以上原子边界。若要改变 V01 恢复语义、接入新调度基础设施或自动执行发布，需要单独调整设计。

## 12. 当前实现边界

现有实现包含五类持久记录、租约/fence repository、单 `run` 步骤的注册 handler runner、独立 worker 命令及游客游览范围的查询/事件/取消/重试 API。内部创建命令只接受 registry 中固定版本且通过严格 Pydantic schema 的工具。当前 registry 为空，没有产品 handler、创建 HTTP 路由或前端执行卡。

W01 revision 更新会在同一 repository 事务内使旧 job 失效；删除会取消活动 job，永久删除清理关联回执、attempt、step、event 和 job。`progress_version` 暂无 W01 字段可供校验；不声称其已保护实际进度变化。迁移、自动化测试、恢复故障注入和 PostgreSQL 多 worker 尚未运行验证；事件裁剪与 30 天 job 清理也未实现。详见配套实施计划和执行记录。
