# 游客历史回答重播设计

## 目标

游客可对当前会话中已完成并保存的回答重新播放语音，不必再次提问。重播使用聊天日志保存的原回答文本，不重新调用问答模型；有语音 profile 的新记录优先用生成时音色，旧记录回退点击时音色；沿用游客本机语速设置和聊天/地图共享播放器。

## 范围与边界

- 只为具有 `chat_log_id` 的已完成回答显示重播入口；欢迎语、临时提示、未完成回答不显示。
- 后端以 `chat_log_id` 和请求中的 `session_id` 联合查找记录，不能只凭自增 ID 读取。
- TTS 未配置或返回空音频时，响应明确标记音频不可用；前端可用浏览器中文朗读降级。
- TTS 失败、会话不匹配和并发容量不足返回明确错误，不生成问答答案。
- 重播使用保存的生成时音色预设及兼容的原 voice ID；旧记录回退请求时音色。偏好语速只在浏览器播放层应用，后端不调速。
- 重播按钮复用共享播放器的会话所有权，新重播会接管并停止旧播放；停止/接管后迟到的网络响应不可启动播放。

## 非目标

- 不保存合成音频、不引入缓存或数据库迁移。
- 不增加聊天历史读取/恢复 API，也不承诺刷新后恢复历史消息。
- 该重播功能本身不保存音频；生成 profile 与内容指纹由后续 V03 语音 profile 设计补充。
- 不改变普通聊天生成、播放和失败重试流程。

## 方案选择

1. 将音频持久化并关联内容/音色版本：可即时回放且版本可追踪，但需存储、清理和版本迁移，本轮清单没有要求这些基础设施。
2. 按会话读取已有答案并按合成配置即时合成：复用现有 TTS，使用进程内有界缓存减少重复调用。**本轮采用此方案**，它满足不重新生成答案并与现有服务边界一致。
3. 仅用浏览器朗读：实现成本最低，但音色与效果随设备变化，也绕过已配置 TTS，不作为唯一方案，仅用作 TTS 不可用时的回退。

## 接口与交互

- `POST /api/chat/replay` 请求体：`chat_log_id: int`、`session_id: str`、`tts_voice: string | null`。
- 响应体：`base64_audio: string`、`duration_ms: int`、`provider: string`、`available: bool`。
- 查无记录或会话不匹配统一返回 404；TTS/基础设施错误返回 503；容量不足遵循现有 429 策略。
- 前端仅对已完成且带 `chatLogId` 的回答展示“重播讲解”。点击后请求后端并接入共享播放器，使用当前语速与音量；返回不可用音频时允许浏览器朗读答案文本。错误显示在对应回答附近。

## 验收

- Repository 查询必须同时匹配日志 ID 和 session ID。
- API 用测试证明会合成保存的准确答案，且不会构建/调用 QA pipeline；错误归属不泄漏答案。
- 前端 API 传递当前会话和当前音色；重播沿用音频播放器会话 ID 和本机语速；迟到响应不入队。
- 相关后端测试、前端测试与构建通过；更新待开发清单、功能地图、架构和多端验证边界。真实设备播放、供应商效果仍标记待实测。
