# 连续伴游恢复：卖点与证据规划

日期：2026-10-29。状态：持久内核代码已在隔离分支实现；真实业务恢复、前端展示和行为证据尚未完成。依据：[调研](../research/2026-10-29-w02-durable-execution-research.md)、[设计](../superpowers/specs/2026-10-29-w02-durable-execution-design.md)。

## 产品表述

拟开发“面向现场变化的连续伴游恢复”：网络中断或服务重启后，系统能找回已保存的任务与步骤；继续之前核对游客的最新行程、已游记录和知识版本，保留人工决定，阻止旧结果覆盖新状态。

当前可以介绍为设计目标；验收后才可改写成“已实现”。持久执行、幂等与检查点均已有成熟先例，创新定位为数字人导游场景的系统组合与可验证适配，不声称行业首创。

当前代码只能支撑内核方案说明：registry 为空，没有产品 handler、任务创建 HTTP 命令或执行卡；不得把下方现场脚本描述为已经可演示的功能。

## 可展示的差异

| 卖点 | 用户看到的行为 | 所需实现证据 | 必须说明的边界 |
|---|---|---|---|
| 有步骤依据的恢复 | 明确哪些已完成、哪些失败、哪些待确认 | 持久 step/event、真实恢复日志 | 生成文字不能冒充执行进度 |
| 尊重现场变化 | 完成景点或手动改线后，旧候选提示复核 | revision/progress 校验、竞争测试 | 无法校验的条件显示未知 |
| 与运营知识同步 | 引用内容被下架，旧任务不能继续沿用 | 发布可见性与版本校验 | 历史引用不赋予读取下架正文的权限 |
| 控制重复成果与计算 | 找回原候选，复用适用步骤，不从头盲目重做 | 持久回执、领域唯一键、调用计数 | 外部调用结果不确定可能再次计费 |
| 双端有一致证据 | 游客确认行程，运营审核发布，各有执行记录 | 领域适配器、隔离鉴权 | 不共享游客私有照片/位置，不自动发布 |

## 现场演示脚本

1. 使用固定演示目录和行程，完成一个景点，锁定另一个。
2. 发起支持后台恢复的讲解草稿任务；展示检索步骤已保存。
3. 在生成阶段终止 worker，前端显示等待恢复或待核查，不显示成功。
4. 在另一标签页更新行程或完成下一景点。
5. 重启 worker、重开页面，展示原任务和已完成步骤；旧基线无法直接应用，要求复核。
6. 对新基线生成/确认可用候选，保存一次成果；展示两 worker 或重复点击仍只有一个业务结果。
7. 另以内容下架场景展示旧任务被阻断，而非继续使用历史正文。

第 2 步依赖 O01 对后台生成流程的确认和实际实现；此前只能使用明确标注的假工具演示内核，不能称为真实数字人内容生产。

## 评测与答辩口径

固定对照组、输入、故障点与版本，记录任务完成率、恢复成功率、事实保持率、旧结果覆盖数、成果重复数、内容失效阻断率、恢复时延、调用数及用量。两种模型方案使用相同供应商、模型和预算。mock 故障测试与真实供应商、真实手机实测分开报告。

验收后可采用：

> 我们将一次游览、每次工具执行和每个步骤分开记录。中断后既能找到已保存结果，也会重新检查行程与知识是否发生变化，让恢复保留游客决定和实际游览记录。

禁止在验证前采用：“断网也能持续运行”“所有 API 只调用一次”“自动恢复任何任务”“绝不重复收费”“性能提升 X%”“行业首创”或“赛题创新分已保证”。
